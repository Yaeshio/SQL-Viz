# GitHub連携によるSQL実行履歴保持機能 仕様書

このドキュメントは [Issue #18「#SQL文実行履歴保持機能の実装」](https://github.com/Yaeshio/SQL-Viz/issues/18)
に基づき、本機能が**何を・なぜ**実現するかを定義するものである。実装方法
（対象ファイル、モジュール構成、依存関係の選定理由）については
[github-sync-design.md](./github-sync-design.md) を参照。

現在の対応SQL構文の一覧・選定理由は [user-stories.md](./user-stories.md) を、
スモークテストとの対応は [smoke-test-spec.md](./smoke-test-spec.md) を参照
（本機能でSQL対応範囲を拡張する際は、両ドキュメントも合わせて更新する）。

## 1. 目的とスコープ

現状 SQL-Viz は、テキストエリアに入力された SQL の実行結果をどこにも
永続化しない（[CLAUDE.md](../CLAUDE.md) が明記する通り、バックエンドや
永続化層を持たないクライアントのみのシングルページアプリである）。この
構成では、教育目的の利用はできても、DB設計時の設計支援ツールとして
運用することが難しい。

そこで、SQLの実行結果を GitHub API を用いてユーザーが選択したリモート
リポジトリへプッシュし、保管できるようにする。このとき、Issue #18 は
次の点を明確に要求している。

> SQL文の実行履歴をすべて同一のJSONファイルにまとめると、スキーマ定義に
> 必要な情報と、クエリ設計などに必要な情報が同一ファイルに同居してしまう。
> この場合、スキーマ定義とそれ以外の情報が混在して設計上必要な情報が
> 整理できない。

したがって、保存対象を次の2種類に分離する。

| 成果物 | 内容 | 保存の性質 |
|---|---|---|
| `schema/ddl.sql` | スキーマ構造（テーブル・カラム）のDDL | 必須・常時保存対象・自動生成 |
| `query-examples.md` | クエリ例 | 任意・ユーザーが明示的に「昇格」した分だけ・Markdownとして自動整形 |

この分離を成立させるために、アプリに**設計モード**と**実験モード**の
切り替えを導入する（2節）。

## 2. モード概念

Issue #18 が定義する2モードの対比表をそのまま採用する。

| | 設計モード（スキーマ編集） | 実験モード（クエリ実行） |
|---|---|---|
| 操作対象 | テーブル・カラム・リレーションの構造そのもの | 既存スキーマに対するSELECT等の読み取り操作 |
| 前提とする状態 | 「今から構造を変える」という明示的な意思 | 「今の構造は固定」という暗黙の前提 |
| 副作用の許容度 | 変更が即座に図・DDLに反映される（想定通り） | 試行錯誤の失敗（構文エラー等）が起きても構造に影響してはならない |
| 保存の単位 | `schema/ddl.sql` のスナップショット | `query-examples.md` への「昇格」操作 |

ここから導かれる2つのハード制約:

1. **実験モードでスキーマ構造が変化してはならない。** 実験モードで
   実行できるSQLは、既存の構造を前提とした読み書き（3節）に限られる。
2. **設計モードではクエリなどを実行できない。** 設計モードはテーブルや
   リレーションの作成などの設計機能に徹する。

## 3. モード別SQL文許可マトリクス

設計モードのテーブル/カラム編集は、新たな構造化GUIを作るのではなく、
既存のSQLテキストエディタ（`SqlEditorPane`）を拡張する方式を採る
（フォームベースのテーブル/カラム編集UIは作らない）。実験モードは
`SELECT` に加え `INSERT`/`UPDATE`/`DELETE` も許可する（GitHubへの
永続化対象になるのは、明示的に昇格された `SELECT` クエリのみ。
`INSERT`/`UPDATE`/`DELETE` はあくまでモード内の試行錯誤であり、
GitHubには一切渡らない）。

| 文種 | 設計モード | 実験モード |
|---|---|---|
| `CREATE TABLE` | ✅ | ❌ |
| `ALTER TABLE`（単一 `ADD COLUMN`/`DROP COLUMN` のみ、4節参照） | ✅ | ❌ |
| `DROP TABLE` | ✅ | ❌ |
| `SELECT` | ❌ | ✅ |
| `INSERT` | ❌ | ✅ |
| `UPDATE` | ❌ | ✅ |
| `DELETE` | ❌ | ✅ |

この許可マトリクスは、`parser.ts` が担う「文法として妥当な `CREATE`/
`ALTER`/`DROP`/`SELECT`/`INSERT`/`UPDATE`/`DELETE` か」という検証とは
**独立した、別レイヤーのゲート**である。前者は常に一定の許可リストで
SQLの構文的妥当性を検証し、後者は「今のモードでその文種が許されているか」
を検証する。両方を通過して初めて実行される。

**実験モードで行ったデータ変更（`INSERT`/`UPDATE`/`DELETE`）は、設計
モードに復帰した時点でリセットする。** 設計モードは常に正準なデータを
前提として構造編集を行うべきであり、実験モードでの試行錯誤の結果を
引き継がせない。

## 4. `schema/ddl.sql` 仕様

- **保存タイミング**: 設計モードでの操作後、ユーザーが明示的に
  「スキーマをプッシュ」した時点。
- **生成方式**: フルスナップショット（差分ではなく、都度ファイル全体を
  再生成して上書き）。生成元は `DBState`（`src/types.ts`）からの
  再構成ではなく、その時点でPGliteが保持する実スキーマ
  （`information_schema`）を正とする。`DBState.Column.type` は
  `normalizeType()` により型が丸められているため、`VARCHAR(50)` の
  長さなどの精度を落とさないためである。
- **範囲**: テーブル定義（列名・型）のみ。制約（`PRIMARY KEY`/
  `FOREIGN KEY`/`NOT NULL`/`DEFAULT`等）はMVPでは対象外
  （リレーション自体をスコープ外とする決定は8節参照）。
- **テーブルの並び順**: `DBState.order`（画面上のレイアウト順）に従う。

## 5. `query-examples.md` 仕様

- **昇格対象**: 実験モードで実行した `SELECT` 文のうち、ユーザーが
  明示的に「昇格」操作を行ったものだけ。`INSERT`/`UPDATE`/`DELETE` は
  昇格の対象にならない（3節）。
- **保持**: 昇格待ちのクエリは、プッシュ前は `localStorage` に保持する
  （タブを閉じてもプッシュ前の内容が失われないようにするため）。
- **フォーマット**: クエリ1件につき見出し（ユーザーが付けたラベル、
  未入力時は連番）＋ ` ```sql ` フェンスで囲んだSQL本文＋任意の
  メモ（自由記述）＋昇格日時（ISO形式）の組み合わせをMarkdownとして
  自動整形する。
- **書き込み方式**: リネームないし上書き（既存の `query-examples.md`
  とのマージ/差分統合は行わない）。

## 6. GitHub連携方式

- **認証**: ユーザーがアプリ内でGitHub Personal Access Token（PAT）を
  入力する。OAuthアプリ・専用バックエンドは用意しない。これは本
  プロジェクトが一貫して維持してきた「バックエンドや永続化層を持たない
  クライアントのみのシングルページアプリ」という構成
  （[CLAUDE.md](../CLAUDE.md)）を崩さないための選択である。
- **プッシュ先**: ユーザーが手動入力した `owner/repo` とブランチ名
  （リポジトリピッカーやブランチ選択UIは現段階では作らない）。
- **API**: GitHub Contents API（`GET`/`PUT /repos/{owner}/{repo}/contents/{path}`）
  を直接呼び出す。実装方式・依存関係の選定は
  [github-sync-design.md](./github-sync-design.md) を参照。
- **`@supabase/supabase-js`との関係**: `package.json` に存在するが
  `src/` のどこからも使われていない未使用依存であり、本機能でも
  利用しない（GitHub Contents APIとは無関係）。

## 7. セキュリティ考慮事項

本アプリは Public リポジトリ上で公開されるクライアント完結型アプリ
であり、PATはユーザーのブラウザ内にのみ保持される。

- **推奨スコープ**: 対象リポジトリに限定した fine-grained PAT
  （Contents の読み書き権限のみ）を推奨する。classic PAT（`repo`
  スコープ全体）は推奨しない旨をUI上でも案内する。
- **保存先**: `sessionStorage` に保持する（タブを閉じると破棄される。
  ページのリロードには耐える）。`localStorage` は保存期間が長く漏洩
  リスクが相対的に高いため採用しない。メモリのみの保持は安全だが
  リロードのたびに再入力が必要になり利便性を大きく損なうため採用しない。
- PATやリポジトリ設定情報をログ（`useSqlRunner` の `log`）やアニメー
  ションイベントに一切含めないこと。

## 8. 対象外

- GitHub OAuthフロー（6節参照）。
- CI上での実GitHubプッシュの自動化。`.github/workflows/ci.yml` には
  現状シークレット/環境変数の利用が一切なく、本機能もそれを変えない
  （[smoke-test-spec.md](./smoke-test-spec.md) §3 がE2Eテストの導入を
  見送った理由づけと同様、実際のネットワークI/Oを伴う検証はCI自動化の
  対象外とし、手動確認に委ねる）。
- 複数リポジトリ/ブランチのピッカーUI（`/user/repos` 等の一覧取得は
  行わない。手動入力欄のみ）。
- テーブル間のリレーション（外部キー）のモデル化・DDL出力・キャンバス
  描画。`types.ts` のモデル拡張・パーサー拡張・キャンバス描画を伴う
  別プロジェクト規模になるため、本Issueのスコープには含めない。
- `ALTER TABLE` の `RENAME`・列の型変更・複数アクションの同時実行
  （4節参照。単一の `ADD COLUMN`/`DROP COLUMN` のみに対応する）。

## 9. 実装マイルストーン別 実施内容

本機能は一度に実装せず、以下の順序（依存関係順）で段階的に実装する。
各マイルストーンの対象ファイル・実装手順の詳細は
[github-sync-design.md](./github-sync-design.md) を参照。本節は、各
マイルストーンが完了した時点で「何が実現されているか」を、本書の各節
（仕様）に対応づけて示すものである。

| マイルストーン | 状態 | 実施内容 | 対応する本書の節 |
|---|---|---|---|
| **M0** ドキュメント整備 | 完了 | 本書・`github-sync-design.md` の作成、`CLAUDE.md` への参照追記。コード変更は行わない。 | 全節 |
| **M1** parser/engineのSQL対応拡張 | 完了 | `ALTER TABLE`（単一 `ADD COLUMN`/`DROP COLUMN` のみ）・`DROP TABLE`・`UPDATE`・`DELETE` を実行可能にする。この時点ではモードによる制限は行わず、全文種が実行できる状態になる（モードゲート自体はM3で追加）。既存の「UPDATE/DELETEは非対応」とする既存テスト・ドキュメント記述の書き換えを伴う。 | 3節（許可マトリクスに列挙されたSQL文種そのものの実装） |
| **M2** 新規AnimationEvent種別とcanvas対応 | 完了 | M1で新たに発生するテーブル削除・カラム追加/削除・行更新・行削除を画面上でアニメーション表示できるようにする。M3以降がユーザーに結果を見せるための前提工程。**目視確認（`/visual-check`）は本セッションのサンドボックス環境でDockerが利用できず未実施**（typecheck/lint/testの自動検証は完了）。 | — （UI表現の前提整備。仕様上の新規節はない） |
| **M3** モード概念とゲーティングUI | 完了 | 設計モード/実験モードの切り替えUI（`ModeToggle`）と、3節のSQL許可マトリクスを実際に強制するモードゲート（`PgEngine.run()`の`mode`引数）を実装した。実験モード→設計モード復帰時のデータリセット（3節）は、実験モード中の全文をPostgresトランザクションに乗せ、復帰時に`ROLLBACK`する方式（`PgEngine.returnToDesign()`）で実現した。 | 2節・3節 |
| **M4** `schema/ddl.sql` 生成 | 未着手 | PGliteの `information_schema` から実際にDDL文字列を生成する機能を実装する。 | 4節 |
| **M5** GitHub PAT/リポジトリ設定とプッシュクライアント | 未着手 | 6節・7節の認証・保存方式に従い、GitHub Contents APIへの接続とスキーマのプッシュを実装する。**着手前に10節に記載のCORS未決事項の解消が必須**。 | 6節・7節 |
| **M6** 昇格フローと `query-examples.md` プッシュ | 未着手 | 5節の仕様に従い、実験モードのSELECT結果を昇格し、`localStorage` を経てGitHubへプッシュする機能を実装する。 | 5節 |

## 10. 未決事項

- **GitHub Contents APIへのブラウザ発 `PUT` のCORS実現可否。** 現時点
  では未検証。`api.github.com` がブラウザオリジンからの認証付き `PUT`
  を許可するかどうかは、実装着手前に実機検証する必要がある。もし
  許可されない場合、サーバーレスプロキシ等の追加が必要になり、
  「バックエンドを持たない」というこのドキュメント全体の前提が崩れる
  ため、その場合は改めてユーザーと方針を確認する。

その他の主要な設計判断（モード切替時のデータリセット方針、
`ALTER TABLE` のMVPスコープ、リレーションのスコープ外化、
`query-examples.md` の書き込み方式、昇格待ちクエリの保持方法、PATの
保存期間、リポジトリ/ブランチ選択UX）はいずれも本ドキュメント作成時点で
ユーザーと確認済みであり、上記各節に確定事項として記載している。
